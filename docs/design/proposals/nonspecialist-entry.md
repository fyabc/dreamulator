# 非专业用户入口：先定高程契约，再做导入面板与可见的计算过程

> 状态：已接受，高程契约与导入面板尚未实现。立项日期：2026-11-04。
>
> 立项 2026-11-04。起因是作者指出本库前端与 [web-exoplasim](../web-gcm-and-frontend.md) 的
> 使用体验反差明显，而可借鉴的三条（迭代过程可见、参数面板即文档、地形导入即用）与「非专业
> 用户导入」是同一件事，应合并做。本文记录现状核查、方案与验收，不记录每日进度。
>
> **核查结论改变了顺序**：导入路径的高程语义目前在「归一化」与「米」之间未定，所以第一步不是
> 做面板，而是先把契约定下来——面板要写明的那些数字，现在还没有唯一含义。
>
> GPL-2.0：web-exoplasim 的代码一行不抄，借鉴限于方法与界面思路。

## 1 现状核查

### 1.1 高程契约未定（必须先修）

导入链上有两套互不相容的高程语义：

- `map/importer.py` 的 `import_heightmap` 按**数据类型范围**归一化（8 位除 255、16 位除 65535），
  输出 [0, 1]，所以归一化值与真实米数之间没有关系，只与图像位深有关。
- `map/voronoi_generator.py` 的 `sample_heightmap` 把归一化值**原样写进** `cell.elevation`，而它
  的 `elevation_min_m` / `elevation_max_m` 两个参数的文档字符串明写「unused, for API compat」
  ——它们是死参数，看起来却像在控制米制映射。调用方 `map/manager.py` 的
  `sync_voronoi_from_elevation` 从 `map.yaml` 读出这两个值并传进去，于是读代码的人会以为映射
  发生了。
- 而 CVT 网格那条路上 `cell.elevation` 是**米**：正典网格的范围是 −7743 到 5360 m，生态与气候
  层按米消费（海陆判据是 `elevation > 0`）。

所以同名字段在两条路上含义不同，且其中一条的转换参数是死的。**在这个状态下无法写「参数面板即
文档」**，因为面板要标注的单位本身还没有唯一答案。这一项先于界面工作。

待核查的一步：`import-elevation` 端点只调用 `sync_voronoi_from_elevation`（旧 `VoronoiNetwork`
路径）并把下游图层标记为 stale，没有看到它更新 CVT 网格；需要确认导入后哪条消费路径实际生效，
以及导入的高程最终以什么单位到达气候层。这决定下一节的面板需要几个数字。

### 1.2 导入界面不暴露任何决策

`components/map/ImportElevationButton.tsx` 全文 73 行，是一个文件选择器加一次
`window.confirm`。它不提供海平面阈值、不提供最大高程、不接受海陆掩膜、不检查长宽比、不预览、
不报告判定出的陆地占比。对照之下 web-exoplasim 的导入面板只要两个数字（灰度海平面阈值、最大
高程）加一张可选掩膜，并把单位与常见错误写在输入框旁边。

本轮有一条直接证据：给 web-exoplasim 导出 nacrea 地形时，导出脚本不得不**预先**把高度图处理成
「水域为零、线性升到陆地最大值」，并在参数清单里写明「阈值取 0」——那是为了配合对方的 cutoff。
我们自己这一侧没有 cutoff 可配，所以同一张图导进本库会得到什么海陆分布，取决于 1.1 的契约，
而不是用户的意图。

### 1.3 计算过程不可见

主地图在构建完成后才出结果，nacrea 200k 全量约 13 分钟（地质约 230 s + 气候约 510 s + 生态 5 s）
期间界面没有可看的中间状态。而引擎已经产出阶段划分（`build_profile.json`）与逐月场，湿槽的外层
迭代也存在，只是都没有暴露。浏览器实验台的温度首图 0.19 s，所以那一页无需过程可视化，但它只算
温度。

### 1.4 入口藏在实验功能后

`/playground` 默认隐藏，要先打开侧栏的「实验功能」才出现。它是目前唯一不需要写 YAML 的路径。

## 2 借鉴的三条与对应动作

| 它的做法 | 本库现状（已核查） | 对应动作 |
|---|---|---|
| 地形导入即用：两个数字加可选掩膜，本地读取不上传 | 文件选择器 + confirm；高程语义未定（1.1） | 先定契约，再做面板（3.1、3.2） |
| 参数面板即文档：单位、范围与常见错误写在输入框旁 | 参数散在 yaml 与提案里 | 面板内联单位与陷阱，与导入合并（3.2） |
| 迭代过程可见：模式一边跑一边出图，图层与时间模式可切 | 构建完才出结果，阶段与逐月场已存在但不暴露 | 把已有阶段与逐月场当时间轴暴露，先做只读播放（3.3） |

## 3 方案

### 3.1 阶段 A：定高程契约（前置，不含界面）

把导入链上的高程统一成**米**，并让转换参数真的生效：

1. `import_heightmap` 增加显式的高程映射入参（海平面灰度阈值与最大高程，或等价的
   最小/最大米数），返回米制数组而不是归一化数组；归一化只作为解码的中间步骤。
2. `sample_heightmap` 的两个死参数要么真正参与计算，要么删除——保留一个文档字符串写着
   「unused」的参数比没有参数更糟，因为它让调用方以为映射发生了。
3. 两条路径（旧 `VoronoiNetwork` 与 CVT 网格）的 `elevation` 字段语义写进
   [地图系统文档](../pipelines/map-system.md)，并加一条测试把语义钉住。

**验收**：导入一张已知的高度图（用本轮 nacrea 的导出图，真实范围 −7743 到 5360 m 已知），导入后
网格高程的范围与陆地面积占比与源数据一致到重采样误差之内。这是一个可以写成测试的判据。

### 3.2 阶段 B：导入面板即文档

契约定下来之后，面板只需要暴露契约里的那几个数字：

- **两个数字**：海平面灰度阈值与最大高程（或最小/最大米数），各自标注单位、合理范围与默认值
  的来源。
- **可选海陆掩膜**：一张同尺寸的黑白图，用来覆盖灰度阈值的判定；没有掩膜时退回阈值。
- **导入前预览**：灰度预览加判定出的海岸线，并显示陆地面积占比。用户在写盘之前就能看到自己
  会得到什么，这是现在最缺的一环。
- **就地警告**：长宽比不是 2:1、位深只有 8 位（256 个高程台阶）、尺寸与目标网格差异过大需要
  重采样——这三条都是已知会咬人的地方，写在面板里而不是留给用户发现。

**验收**：一位没读过本库文档的人，能在不打开 yaml 的情况下导入一张自己的高度图，并在写盘前
确认陆地占比符合预期。

### 3.3 阶段 C：计算过程可见

- **阶段进度**：构建时把 `build_profile.json` 已有的阶段划分作为进度推给前端，先做文字阶段名
  加耗时，不做曲线。
- **逐月播放**：月度场已经落盘（`climate_monthly.msgpack`），前端已有 `TimeControl` 与
  `SunControl`；把两者接成「年均 / 逐月」的只读播放，对应它的 Annual / Monthly 两种模式。
  它的 Now 模式对应瞬时状态，本库只有在气象图层包（高频快照）存在时才有对应物，所以 Now
  这一档只在有图层包的世界上出现。
- **不做**边跑边出图的流式渲染。本库是诊断式 DAG 而不是时间积分模式，没有「每步一帧」的天然
  产物；强行造一个会把引擎结构往时间积分方向拖，与架构相反。

### 3.4 阶段 D：入口与默认

把 `/playground` 从「实验功能」后面放出来，作为非专业用户的默认入口，并在首页给一条明确的
「我只想导一张图看看气候」的路径。前提是阶段 A 与 B 完成——在高程语义未定、面板不预览的状态下
把入口放出来，只会让新用户更快地得到一个他不理解的结果。

## 4 排期与依赖

阶段 A 是其余三个阶段的前提，而且它本身是引擎侧的小改动加测试，不依赖任何人。阶段 B 依赖 A。
阶段 C 的逐月播放不依赖 A/B，可以并行；阶段进度推送需要 API 侧的一个进度通道。阶段 D 依赖
A 与 B。

与 [浏览器气候实验台](browser-playground.md) 的关系：那份提案回答「浏览器里能不能算」，本文
回答「非专业用户怎么进来」。实验台的完整气候仍受降水预算成本约束（提案 §7），但导入与面板
这两件事与算得多快无关，可以先做。

## 5 不采用的方向

- **抄它的界面代码**：GPL-2.0 与本库许可不兼容。借鉴限于方法与布局思路。
- **把导入做成服务端唯一路径**：它的本地读取不上传是一个真实优点（隐私与延迟），本库的实验台
  已经走本地路径，导入面板的预览也应在本地算完再决定是否写盘。
- **边跑边出图**（见 3.3）：与诊断式 DAG 的结构相反。
- **在契约定下来之前先做面板**：面板的价值全在于它标注的数字有唯一含义；先做面板等于把一个
  未定的语义固化到界面上。
