# 参数归属、输入投影与数据漂移防护

> 状态：部分实现。数据去重与参数登记表首批已实现（2026-11-24）；按层输入投影与参数实验台未实现。
> 更新历史：

> - 2026-11-24：数据去重实现。nacrea 的 `stellar.yaml` 删除 85 个重复物理字段，地球删除 2 个；重建天文层后目录物理值逐项不变，只少掉三条重复警告。三处自转分歧按 `planets.yaml` 裁决：Ember 5.56、Crucible 17.65、Vigil 10.29。重复扫描接入 `validate`。
> - 2026-11-24：参数登记表首批实现。四个行星物理参数写入签入仓库的 JSON，后端加载与前端别名共用同一份；引擎声明消费者，测试锁定登记表与引擎声明一致。

本文定义世界输入参数的统一模型：参数归哪个学科、哪些层真正读取它、值写在哪里，以及如何据此判断某一层是否需要重算。它同时给出数据漂移（同一个值在多处手写并逐渐不一致）的检测与治理方案。参数实验台的交互由[开发工作台](development-workbench.md)维护，本文只定义它依赖的数据模型。

## 1 问题与目标

### 1.1 三个已有问题

第一，**归属与影响被混为一谈**。邦德反照率住在 `layers/geological/input/planets.yaml`，层新鲜度按文件 mtime 判断，于是修改反照率会把地质层标成「输入已改」。但默认地形相位不读反照率，真正读取它的是气候辐射平衡与天文平衡温度。文件归属不等于计算依赖。

第二，**参数跨学科**。轴倾角、自转周期在界面上被理解为天文参数，但地质层用倾角计算极地冰盖、用自转判断潮汐锁定，气候层用两者计算季节与科氏力。按「参数属于哪个层」决定标脏范围，会漏掉其他消费者。

第三，**同一个值被多处手写，已经开始漂移**。nacrea 的 `layers/astronomy/input/stellar.yaml` 与 `layers/geological/input/planets.yaml` 同时手写了天体的自转周期、轴倾角与反照率。抽查发现至少三处自转周期已经不一致：守珠星为 10.2 与 10.29 地球日，赤星为 5.37 与 5.56，熔炉星为 16.6 与 17.65。倾角与反照率目前一致，但没有机制保证它们继续一致。

### 1.2 本次要解决

- 给每个可编辑参数一个明确的三元组：归属组、消费者、存储位置。
- 用消费者而不是文件位置判断层新鲜度与构建起点。
- 让参数实验台只保存输入，正式构建只有一个入口。
- 让本地世界与浏览器高度图世界共用同一套参数模型与构建语义。
- 防止同一个值在多处手写，并在已经漂移时给出可执行的检测报告。

## 2 三个概念

| 概念 | 回答的问题 | 用途 |
|------|-----------|------|
| 归属组 | 这个参数在界面上归哪个学科？ | 实验台分组、编辑入口 |
| 消费者 | 哪些引擎的计算真正读取它？ | 标脏、构建起点、影响提示 |
| 存储位置 | 值写在哪个输入文件、哪一条路径？ | 保存、分支继承、校验 |

三者必须分开。以轴倾角为例：

- 归属组是天文，因为作者在「天文参数」里调整世界观的天体姿态；
- 消费者是天文、地质与气候：天文目录记录该值，地质层用它计算极地冰盖，气候层用它计算季节；
- 存储位置是 `planets.yaml` 中的 `planets[*].axial_tilt_deg`。

因此保存轴倾角应当标记天文、地质、气候三层，构建从最早的受影响层开始，下游显示「上游已改」。界面不应承诺「只标天文」。

反照率同理：归属组可以是气候（作者把它当作气候辐射参数调整），消费者是天文与气候，地质不是。归属组的划分按作者心智模型，不按物理归属。

## 3 参数登记表

参数登记表是参数的唯一声明处。它用签入仓库的 YAML 或 JSON 保存，后端与前端共同读取：后端用于校验、投影与保存，前端用于实验台分组、范围校验与影响提示。前端在打包时导入生成好的模块，静态站与浏览器世界不依赖额外网络请求。

每条记录包含：

```yaml
id: planet.axial_tilt_deg
group: astronomy
storage:
  file: layers/geological/input/planets.yaml
  path: [planets, "*", axial_tilt_deg]
type: number
unit: deg
range: { min: 0, max: 90 }
consumers: [astronomy, geological, climate]
note: 地质层用于极地冰盖，气候层用于季节，天文目录记录该值。
```

字段说明：

- `id` 是稳定标识，界面与投影记录都引用它，不使用文件路径或中文标签。
- `group` 是归属组，取值来自层级枚举；它只影响实验台分组，不影响标脏。
- `storage.file` 与 `storage.path` 是唯一的手写位置，路径支持按天体 id 或列表通配。
- `type`、`unit`、`range` 用于前后端共同校验；后端仍以输入模型的 schema 为最终判据。
- `consumers` 是消费者层列表，必须来自引擎声明并经测试锁定（见 §7）。

第一切片登记四个行星物理参数：轴倾角、自转周期、邦德反照率、温室增温。网格规模与水覆盖需要处理替代输入文件与派生存储，在参数实验台接入网格编辑时补充。其他文件暂不登记，按整文件投影处理。

登记表不追求穷举所有 authored 字段。只有两类参数需要逐字段登记：界面可编辑的参数，以及被多个层共享的参数。只被一个层读取的字段继续使用整文件哈希即可，未登记字段的保守回退保证「多算一层」而不是「漏算」。因此增补是按需的、增量的，不影响已有字段的正确性。

增补成本主要在消费者审计，而不是 JSON 本身。同层字段通常只需一条登记与一次模板路径测试；跨层字段需要确认每个消费者并同步引擎声明，测试会强制两边一致。真正耗时的是界面控件与文案。新增登记项会让旧的投影记录缺少该字段，下一次构建前相关层回退到文件 mtime 或标脏一次，这属于一次性成本。

## 4 按层输入投影

### 4.1 投影的定义

每一层对自己的输入做一次投影：只取出该层消费者声明里列出的参数值，规范化后计算哈希。对没有登记的文件，投影就是整个文件的哈希。

例如气候层的投影包含邦德反照率、温室增温、轴倾角、自转周期与气候强迫文件，不包含地质层的水圈与岩圈字段。地质层的投影包含轴倾角、自转周期、水覆盖、网格规模与地形配置，不包含反照率。

保守原则：字段漏登记时，宁可多标一层，不能漏标。未登记的文件与字段使用整文件哈希；未登记字段出现在共享文件里时，读取该文件的所有消费者都视为受影响。

### 4.2 记录与比较

构建成功后，每层把本次投影写入 `layers/<layer>/derived/.input-projection.json`（派生目录不入库）。格式包含 schema 版本、层名与按文件分组的哈希。

层状态改为比较「当前投影」与「记录投影」：

- 一致为 `fresh`；
- 不一致为 `stale`；
- 没有记录时回退到当前的 mtime 判断，保证老世界在下次构建前仍可使用。

构建计划沿用同一套状态：最早 `stale` 的层是起点，之后的层显示为将重算；界面把起点之后的 `fresh` 层显示为「上游已改」。

### 4.3 分支与浏览器

投影按「分支 → 根」的顺序解析，与派生目录一致。分支只重算气候时，地质沿用根的投影记录；分支自己构建过的层使用分支的记录。

浏览器世界的适配器把登记表里的逻辑路径映射到项目存储；投影在浏览器内计算，记录与构建计划写回项目。构建执行器不同，状态、计划与标脏语义相同。

高度图世界也走同一套构建流程，只是计划从导入高程的层开始，跳过前面的生成步骤。参数实验台只展示与这些层相关的参数。

### 4.4 记录值不等于依赖值

派生文件里也会出现输入值的副本，例如 `climate_metadata.json` 记录反照率与温室增温。这类副本是输出元数据，不构成计算依赖。规定：

- 派生元数据由拥有该值的层写入，其他层不重复计算同一元数据；
- 登记表只登记计算输入，不登记输出元数据；
- 迁移时把地质导出中的气候元数据交给气候层写入，避免修改反照率时把地质层拖进重算。

## 5 参数实验台

参数实验台只做三件事：编辑参数、校验、保存。它不再运行任何计算。

### 5.1 界面职责

- 按归属组分组：天文、气候、地质。每组显示参数、单位、范围与来源文件。
- 每个参数显示它的消费者层，例如「轴倾角 · 影响：天文、地质、气候」。
- 保存提供两个落点：「保存到当前分支」与「另存为分支」。
- 保存成功后显示「将重算：…」与「前往构建」，并刷新顶栏的构建计划。
- 没有「运行」「构建气候」「保存试算结果」等计算按钮。

### 5.2 试算的退役

气候实验台当前的试算走的就是气候层完整链路，与正式构建同一量级，不能提供更快的反馈；对气候层做粗略快速估算也没有实际价值。因此 API 模式的试算作为独立计算入口退役：

- 参数修改后保存，再在顶栏发起正式构建；
- 需要保留一组方向时，使用「另存为分支」，构建分支后比较；
- 历史保存的试算结果保留只读，不再产生新的。

浏览器高度图世界不是例外：它有自己的构建流程，只是从导入高程的层开始，与本地模式同构。浏览器构建是正式构建，写入项目派生数据，不是试算。

### 5.3 正式/开发开关

气候开发结果的生产者就是试算。试算退役后，API 模式的世界暂时没有气候开发结果：

- 保留结果模式机制，供后续按层开发结果与浏览器构建使用；
- 没有开发结果时，开关不可用或明确显示「尚无开发结果」；
- 不在这一轮移除开发模式本身。

### 5.4 气候模型

气候模型不是参数实验台里的普通参数。正式构建的模型选择已经存在：分支元数据 `climate_source`（`engine` 或 `gcm`），保存到 `branch.yaml`。模型选择属于分支级设置，不写入气候层输入文件，避免形成第二个事实源。

只暴露已经实现并通过验收的模型。EPS 与 EPS++ 在实现前不作为可保存选项出现。

## 6 构建与计划

正式构建只有一个入口：顶栏的构建计划与构建按钮。

- 参数保存只写输入，不触发计算；
- 投影变化决定哪些层 `stale`；
- 构建计划从最早的受影响层开始，列出将重算的层链；
- 构建完成后派生数据原地刷新，计划重新读取投影；
- 高度图世界、分支世界与根世界使用同一套计划语义，只是可构建的层集合不同。

## 7 数据漂移防护

归属与投影解决的是「改了一个值，应该重算哪几层」。它们本身不能阻止同一个值被写两遍。防漂移需要以下机制一起生效。

### 7.1 唯一写入点

每个参数 id 在登记表里只有一个存储位置。参数实验台是这些字段的唯一编辑入口；直接手写 YAML 仍然可能，但会被校验发现。派生文件永远不是写入点。

### 7.2 唯一解析点

引擎通过共享的模型加载函数读取参数，返回「值 + 来源」（作者输入、分支覆盖、默认值）。计算代码不直接读原始 YAML 键；现有代码中用于一致性警告的原始读取保留，但不得成为第二条计算路径。

### 7.3 重复声明扫描

新增 `validate` 深度检查（或独立脚本）：对每个参数 id，沿有效输入链找出所有声明位置，包括登记表标记的历史镜像。报告两类问题：

- 同一作用域内出现多处手写；
- 权威位置与历史镜像的取值不一致。

扫描同时检查未登记字段：共享文件中出现登记表之外的可编辑字段时给出警告，并按保守规则把它计入所有读取该文件的消费者的投影。天体物理字段另有一条完整性检查：不在 `planets.yaml` 中的天体必须自备质量与半径，避免删除重复字段时把数据一起删掉。

### 7.4 镜像策略与迁移

允许在迁移期保留历史镜像，但要求它与权威位置完全一致；校验不通过时构建前提示。迁移完成后删除镜像。

对本案的具体迁移：

- 行星与卫星的物理参数以 `planets.yaml` 为权威，与现有创作规范一致；
- `stellar.yaml` 只保留恒星参数与天体轨道/身份信息，重复的物理字段删除；
- 天文目录按天体 id 与 `planets.yaml` 连接取值；
- 模板、nacrea 与其他世界同步迁移；
- 迁移前列出所有重复与分歧，交由作者确认每个字段的权威值。已发现的三处自转周期分歧必须逐一裁决。

全库扫描的结果是：nacrea 有 17 个共享天体、85 个重复物理字段，其中 3 个数值分歧；地球有 1 个共享天体与 2 个重复字段；模板与分支没有重复。因此第一轮迁移修改 nacrea 与地球的 `stellar.yaml`。

三处分歧的处理如下：

- **鼎星 Crucible 17.65 与 16.6。** `planets.yaml` 的注释明确说明旧值 16.6 与旧轨道周期不符并已修正，系统目录也已经使用 17.65。保留 17.65，删除 `stellar.yaml` 中的 16.6。
- **守珠星 Vigil 10.29 与 10.2。** 卫星架构记录 0009 给出定版实测 10.286 地球日，系统目录已经使用 10.29。保留 10.29，删除 `stellar.yaml` 中的旧中值 10.2。
- **焦星 Ember 5.56 与 5.37。** 作者裁决保留 `planets.yaml` 的 5.56 作为现行正典，不另案处理；5.37 作为陈旧副本删除。

迁移已经执行：

1. 天体索引的每个消费方都以 `planets.yaml` 覆盖 `stellar.yaml` 的同名字段，包括目录构建、天球几何、潮汐锁定与卫星动力学。
2. nacrea 与地球的 `stellar.yaml` 删除共享天体的重复字段；Aegis 的自转与倾角机制说明移入 `planets.yaml`，避免随副本一起丢失。
3. 重建天文层并对比 `system_catalog.yaml`：天体物理值逐项不变，只少掉三条重复警告。
4. 重复扫描已接入 `validate` 与测试；模板当前干净，新增世界依赖校验避免再次出现重复。

### 7.5 派生数据只读

派生数据由构建生成，手工修改属于错误。构建清单与校验和用于发现被改动的派生文件；参数实验台不提供派生文件的编辑入口。

### 7.6 登记表与引擎声明互相校验

每个引擎声明自己消费的参数 id。测试断言登记表的 `consumers` 与引擎声明完全一致。这防止登记表本身漂移：消费者漏写会导致该层不标脏，消费者多写只会多算一层。

### 7.7 默认值来源记录

参数解析结果记录来源。正式构建使用引擎默认值而登记表认为该参数应由作者输入时，给出警告。这样既不会把 Earth 默认值静默当成世界设定，也不会把默认值误判为作者输入。

### 7.8 元数据单写者

同一项派生元数据只由一个层写入。当前地质导出写入了气候元数据，迁移时移交气候层。跨层复制元数据时从权威派生文件读取，不重新计算。

### 7.9 分支范围

分支覆盖是有意的第二份输入，不属于漂移。规则是：同一作用域内不得重复声明；跨作用域沿继承链解析出唯一有效值；分支覆盖在实验台里明确标注。

### 7.10 防漂移与投影的关系

投影保证「值变了，重算正确的层」；唯一写入与重复扫描保证「值只在一处被改」。两者缺一不可。只做投影而不清理重复声明，下一次仍会在两个文件之间漂移；只做去重而不做投影，改一个共享值仍会标错层。

## 8 迁移与落地顺序

1. **登记表与审计。** 建立参数登记表与重复声明扫描，先只报告不改变行为。审计范围是 planets.yaml 的消费者、stellar.yaml 的重复字段与三处已知分歧。
2. **投影与状态。** 为第一切片的参数实现按层投影、构建成功记录与状态比较；没有记录时回退 mtime。构建计划与界面沿用新状态。
3. **参数实验台。** 实验台改为只保存参数，按登记表分组并显示影响层；保存刷新构建计划；API 模式的试算入口退役；结果模式做最小收尾。
4. **去重迁移。** 按审计结果清理 stellar.yaml 与 planets.yaml 的重复字段，迁移模板与 nacrea，把重复校验接入 `validate` 与 CI。三处自转周期分歧由作者裁决。
5. **扩展与收口。** 把登记表扩展到其他共享输入文件，待所有老世界重建过一次后移除 mtime 回退。

第 1、2 步是第 3 步的前置：没有正确的投影，实验台的保存无法标对层。第 4 步可以在第 3 步之后进行，但必须在下一次数据发布前完成。

## 9 已否证方向与边界

- **先拆文件、后做登记表。** 拆分文件不能解决一个值被多个消费者读取的问题；归属仍然需要消费者声明。
- **为反照率写特例。** 按字段名硬编码一次可以解决当前案例，但下一个共享字段会重新出错。
- **共享文件一变就把所有读取者标脏。** 安全但昂贵，会让改一个反照率触发地质重算。只作为未登记字段的保守回退。
- **把试算结果当作气候的开发结果。** 试算与正式构建走同一链路、成本相同，不能提供更快反馈；改为参数实验台加正式构建，保留方向用分支。
- **认为归属组决定重建范围。** 轴倾角归天文，但地质与气候都读取它；按归属组标脏会漏算。

## 10 开放问题

- 投影记录的具体文件格式与位置，是否需要在构建清单里同时登记。
- 迁移期历史镜像是否允许长期保留为只读说明，还是必须删除。
- 浏览器世界的投影与构建计划是否完全在前端计算，还是由本机服务代算后下发。
- 老世界在从未重建过的情况下如何逐步从 mtime 回退迁移到投影记录，是否需要一次性回填工具。
- 未登记共享文件的整文件哈希在大型输入上的成本与缓存策略。
